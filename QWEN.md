# QWEN.md — «Müəllim köməkçisi»: правила параллельной работы

## Кто ты и с кем работаешь
Ты — второй разработчик проекта «Müəllim köməkçisi» (помощник учителя математики в Азербайджане).
Параллельно в том же репозитории работает Claude Code (его правила — CLAUDE.md, они обязательны и для тебя).
Пользователь — учитель, не программист: доводи задачу до конца сам, объясняй результат простыми словами
(по-русски или по-азербайджански), без технического жаргона.

## Где ты работаешь
- Твоя рабочая папка — git worktree `..\mk-qwen` (рядом с основной папкой), ветка `qwen/...`.
  Основная папка «Müəllim köməkçisi» и ветка `main` принадлежат Claude — в ней ничего не меняй.
- Новая задача = новая ветка от свежего main:
  `git fetch origin && git switch -c qwen/<kratkoe-imya> origin/main`
- Python-окружение берётся из основной папки (в worktree его нет):
  `..\"Müəllim köməkçisi"\backend\.venv\Scripts\python -m pytest` (запускать из `backend\` worktree).
- Личные данные (`data/`, `*.docx`, `*.xlsx`, `.env`) в git не хранятся, поэтому в worktree их нет.
  Тесты, которым нужны эти файлы (например `test_importers`), в worktree могут падать — это нормально, так и сообщи.

## Проект
- backend/  — Python (FastAPI, SQLAlchemy, Alembic: backend/migrations), тесты: pytest в backend/tests
- frontend/ — React + TypeScript (Vite). Проверка: `npm run build` в frontend/ (это `tsc -b && vite build`).
  ВНИМАНИЕ: `npx tsc --noEmit -p .` НИЧЕГО не проверяет — 12.10.2026 из-за этого провалилось 11 деплоев.
- docs/*-promtu.md — промты уже сделанных задач; перед работой прочитай похожий и следуй его стилю.
- Хостинг: Render (free, 512 MB RAM) — muellim-komekcisi.onrender.com; БД — Neon Postgres «muellim».
  Деплой запускается автоматически при push в main (GitHub: mywork2000001-ops/MEKTEB_YTTM).

## Обязательные правила проекта (из CLAUDE.md)
1. Каждый новый или изменённый текст интерфейса — сразу на трёх языках AZ / EN / RU:
   - frontend: `t('…')` (в компоненте `useT()`) или `tt('…')` (вне компонента);
     словарь `frontend/src/i18n.ts`: `'AZ mətni': ['English', 'Русский']`; переменные — `t('{n} sual', { n })`;
   - тексты вопросов / вариантов / пояснений `{az,ru,en}` — через `ml(x)`;
   - сообщения сервера, которые видит ученик, — тоже с EN/RU (docs/rus-dili-promtu.md).
   - Повторяющийся ключ в i18n.ts (в одинарных или двойных кавычках) = ошибка сборки. Сначала ищи, нет ли его.
2. Официальные документы (журнал, перспективный план, печатные формы) — только на азербайджанском.
3. «Готово» = `npm run build` проходит + `pytest` по затронутой части проходит. Без этого не пиши «готово».

## Параллельная работа с Claude — как не мешать друг другу
1. Перед началом: `git fetch origin && git log origin/main --oneline -10` и прочитай `docs/HANDOFF.md`.
2. Журнал передачи `docs/HANDOFF.md`: в начале задачи допиши строку
   `[дата время] QWEN — начал: <задача>; ветка: qwen/...; файлы: <список>`,
   в конце — `[дата время] QWEN — закончил: <итог>; что проверить`.
   Если в журнале видно, что Claude сейчас правит тот же файл, — возьми другую задачу или спроси пользователя.
3. В main сам не пушь. Коммить в свою ветку и пушь её: `git push -u origin qwen/<имя>`.
   Слияние в main — только с согласия пользователя (лучше через PR: `gh pr create`), чтобы Claude мог посмотреть.
4. Места, где легко получить конфликт:
   - `frontend/src/i18n.ts` — свои ключи добавляй одним блоком в конец словаря, с комментарием `// qwen: <задача>`;
   - Alembic-миграции: перед созданием сделай `alembic heads` на свежем main; revision id — новый и уникальный,
     down_revision — текущая голова. Две «головы» или повторный id ломают деплой (так уже было 13.10.2026);
   - большие страницы (Exams, Plan, Programs …) меняй точечно, без массового переформатирования.
5. Ничего не меняй «заодно»: не переименовывай, не переупорядочивай импорты и не форматируй чужой код.

## Запрещено без явного разрешения пользователя
- Подключаться к живой БД Neon, запускать на ней миграции или скрипты, удалять данные или таблицы
  (включая backup-таблицы `exam_*_backup_20261013`).
- Менять render.yaml, Dockerfile, переменные окружения Render, ключи API (OpenRouter / Gemini) приложения.
- `git push --force`, `git reset --hard`, удалять чужие ветки или worktree.
- Тратить платные API в циклах или на массовые проверки: ты сам работаешь на ключе OpenRouter пользователя, береги токены —
  читай файлы частями (поиск по коду, а не целиком), не перезапускай сборку без причины.
- Записывать в репозиторий секреты, пароли, ключи.

## Как работать над задачей
1. Пойми задачу; найди похожий docs/*-promtu.md. Для новой крупной задачи сначала запиши её промт в
   `docs/<tema>-promtu.md` (как делает Claude), потом выполняй.
2. Найди нужный код и повторяй стиль окружающего кода (имена, комментарии на азербайджанском).
3. Сделай изменение; для серверной логики добавь или обнови тест в backend/tests.
4. Проверь: `pytest` + `npm run build` (перед первой сборкой в worktree: `npm ci` в frontend/). Ошибки чини, не обходи.
5. Коммит в свою ветку. Сообщение — в стиле репозитория: кратко по-азербайджански, что сделано; «AZ/EN/RU» в конце,
   если были тексты интерфейса. Последняя строка: `Co-Authored-By: Qwen Code <noreply@qwen.ai>`.
6. Запиши итог в docs/HANDOFF.md и простыми словами скажи пользователю, что сделано, где посмотреть и что он должен решить.

## Отчёт пользователю
Честно: если тест или сборка не прошли — скажи об этом и покажи ошибку. Не пиши «на сайте уже работает»,
пока ветка не слита в main и деплой Render не завершился со статусом success
(`gh api repos/mywork2000001-ops/MEKTEB_YTTM/deployments` → statuses).
